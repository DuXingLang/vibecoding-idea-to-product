> **从产品想法到交付上线的全流程 AI 开发规范**

## 📖 简介

**VibeCoding — Idea to Product** 是一个为 Claude Code 量身打造的 Agent Skill，它定义了一套完整的、可落地的产品开发工作流：

```
PRD → UI 原型 → 技术方案 → 准备开发 → 小步迭代开发 → 系统测试 → 部署上线
```

当你有一个产品想法，但不知道如何开始，或希望 AI 按结构化流程帮助你开发时，这个 Skill 就是为你准备的。它**确保每个阶段都有明确的产出物和确认环节**，避免 AI 自由发挥、代码失控。

---

## 🤔 为什么需要这个项目？

AI 编程能力越来越强，但"让 AI 从零到一开发一个完整产品"仍然充满挑战：

| 常见问题 | 后果 |
|---------|------|
| 🤯 AI 方向跑偏，代码越写越偏 | 写了大量无用的代码，反复返工 |
| 📚 上下文窗口有限，无法完整追踪需求 | 需求前后矛盾，功能实现不一致 |
| 🎨 跳过设计直接编码 | 产品缺乏统一视觉风格，用户体验差 |
| 🔧 擅自引入未声明的依赖或修改核心逻辑 | 代码失控，维护成本飙升 |
| 🧪 只覆盖"快乐路径"，忽略边界情况 | 上线后bug频出，用户信任度降低 |
| 📄 代码完工但文档缺失 | 后期维护困难，新成员无法上手 |

**本项目的核心价值**：通过一套**结构化的 7 阶段工作流**，让 AI 在明确的约束和边界内有序推进，从产品定义到代码交付，每一步都可审查、可验证、可回溯。

## 🚦 快速开始

### 前置条件

- [Claude Code](https://claude.ai/code) 已安装（CLI 或 VS Code 扩展均可）
- 你有一个产品想法（任何形态皆可）

### 安装方式

#### 方式一：直接使用（推荐，适合从零开始的新项目）

```bash
# 克隆项目
git clone https://github.com/DuXingLang/vibecoding-idea-to-product.git

# 进入项目目录
cd vibecoding-idea-to-product

# 启动 Claude Code
claude
```

然后，对 Claude 说出触发词：

> **"我有一个想法，我想做一个产品"**

Claude 会自动识别并进入 7 阶段工作流，从 Phase 0 前置检查开始引导你。

#### 方式二：作为全局 Skill 安装（适合在已有项目中使用）

```bash
# 复制 SKILL.md 到 Claude Code 全局 Skills 目录
cp SKILL.md ~/.claude/skills/vibecoding-idea-to-product.md

# 在任意项目目录中启动 Claude Code
cd /path/to/your/project
claude
```

#### 方式三：项目级安装

```bash
# 将 SKILL.md 放置到项目根目录
cp SKILL.md /path/to/your/project/claude/
```

### 触发词

启动后，输入以下任一关键词即可进入工作流：

```
我有一个想法
我想做一个产品
帮我从零开发一个
我要从想法到上线
我们一起做个产品吧
从零开始做一个项目
恢复进度
```

### 验证安装

启动 Claude Code 并输入触发词后，如果 Claude 开始进行 Phase 0 前置检查（工作目录状态、Git 仓库检查等），说明安装成功。

## 📋 七阶段工作流详解

### 流程总览

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  阶段一      │ →   │  阶段二      │ →   │  阶段三      │ →   │  阶段四      │
│  产品定位    │     │  UI 原型    │     │  技术方案    │     │  准备开发    │
│  → PRD 草稿  │     │  → 设计规范  │     │  → 技术文档  │     │  → 架构宪法  │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
                                                              │
                                                              ▼
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  阶段七      │ ←   │  阶段六      │ ←   │  阶段五      │
│  部署上线    │     │  系统测试    │     │  正式开发    │
│  → 文档同步  │     │  → 测试报告  │     │  → 小步迭代  │
└─────────────┘     └─────────────┘     └─────────────┘
```

### 各阶段说明

#### Phase 0：前置检查

**目标**：确认工作环境就绪，检测是否可恢复历史进度。

| 检查项 | 说明 |
|--------|------|
| 📂 工作目录状态 | 空目录 or 已有代码？从零开始 or 继续开发？ |
| 🗂️ Git 仓库 | 是否已初始化？是否有未提交改动？ |
| 📑 恢复检测 | 检查 `docs/` 目录，判断是否可恢复历史进度 |
| 💡 想法确认 | 开发者是否已有明确想法？或需要一起 brainstorm？ |

---

#### 阶段一：产品定位

**目标**：充分理解开发者意图，产出可落地的产品需求说明书（PRD）。

Claude 会依次提出 8 个关键问题（每次 1-2 个），包括：目标用户、使用场景、核心功能、产品形态、成功指标等。回答完成后，Claude 整理成结构化 PRD 草稿，逐项确认后生成 `docs/prd.md`。

**设计理由**：AI 编程最大的风险是"方向性错误"。本阶段在编码前锁定产品方向，避免后续大规模返工。

📄 **产出**：`docs/prd.md`

---

#### 阶段二：UI 原型设计

**目标**：将需求转化为可视化的交互原型，沉淀设计规范。

| 步骤 | 内容 |
|------|------|
| 1️⃣ 布局方案 | 提供 3 种布局方案供选择 |
| 2️⃣ 交互流程 | Mermaid 流程图绘制 + 审查确认 |
| 3️⃣ 风格配色 | 提供 2-3 套配色方案供选择 |
| 4️⃣ 高保真原型 | 生成可交互的 HTML/CSS/JS 原型（浏览器中直接预览） |
| 5️⃣ 设计规范 | 沉淀为文档，包含配色、字体、交互规范、可访问性要求 |

**设计理由**：视觉反馈是发现需求漏洞最有效的方式。用户在看到原型之前，往往无法准确描述自己想要什么。先看到、再编码，大幅降低返工成本。

📄 **产出**：`docs/design.md` + `docs/ui-prototypes/`

---

#### 阶段三：技术方案

**目标**：设计可直接交付开发的技术架构，冻结技术选型。

Claude 会先询问开发者是否有技术偏好，如无则根据产品形态推荐最佳方案。生成的 `docs/techsol.md` 包含：

- 系统整体技术架构（Mermaid 架构图）
- 各层技术选型及理由（含选型对比表，每项至少 2-3 个候选方案）
- 数据模型设计（ER 图）
- 部署架构方案
- 安全考虑清单（认证、加密、XSS/CSRF 防护）
- 性能预算（首屏加载、API 响应时间、资源体积）
- 外部资源需求清单

**设计理由**：技术选型一旦确定并开始编码，修改成本会迅速上升。本阶段在编码前冻结技术栈，避免后续反复切换。

📄 **产出**：`docs/techsol.md`

---

#### 阶段四：准备开发

**目标**：建立不可轻易变更的规范边界，防止 AI 编程失控。

生成 `docs/architecture.md`，作为开发的"宪法"，包含：

- 技术栈清单（最终确定）
- 目录结构约定
- AI 引用规则（限定可引入的依赖）
- 开发约束（命名规范、代码风格）
- 禁止破坏的核心逻辑（如认证、支付流程）
- 版本控制策略（提交规范、回滚方案）
- 环境变量管理规范

**设计理由**：AI 编程的一个常见问题是"过度发挥"——擅自引入未声明的库、修改核心逻辑、创建不符合架构的代码。本阶段通过明确的约束边界来防止这些问题。

📄 **产出**：`docs/architecture.md` + `.env.example`

---

#### 阶段五：正式开发

**目标**：按任务清单顺序，安全可控地完成所有模块开发。

Claude 首先生成 `TODO.md` 任务清单，然后按**小步迭代模式**逐项开发。每轮迭代前输出以下六项内容，待开发者确认后方可编码：

```
📌 修改目标：本任务完成什么
📁 允许修改范围：可修改的文件或模块列表
🚫 不允许破坏的逻辑：参照 architecture.md 中的核心逻辑
⚡ 对其它模块的影响：预估影响范围及缓解措施
✅ 验收标准：如何算完成任务
🧪 单元测试计划：打算如何验证
```

**任务失败处理**：最多尝试 3 轮修复 → 仍失败则 `git reset --hard` 回滚 → 标记为 `[阻塞]` 跳过 → 请求人工介入。

**设计理由**：AI 一次处理大量代码时，容易出现"局部正确、整体错误"的情况。小步迭代模式通过限制单次修改范围，让每次修改都可审查、可验证、可回滚。

📄 **产出**：`TODO.md` + 功能代码（增量提交）

---

#### 阶段六：系统测试

**目标**：确保产品质量达到可交付标准。

| 测试项 | 内容 |
|--------|------|
| 🔍 全量代码审查 | 代码健壮性、潜在逻辑错误、AI 幻觉检查 |
| 🛡️ 安全扫描 | `npm audit`、硬编码密钥检查、XSS/CSRF/SQL 注入防护 |
| ⚡ 性能基准 | Lighthouse 评分（≥80）、API 响应时间达标 |
| 🧪 单元测试 | 运行全部测试，补充缺失覆盖的核心逻辑 |
| 📋 需求回溯 | 逐条对照 PRD 中的功能点，检查是否有遗漏 |
| ✅ 整体验收 | 正常 + 异常 + 边界情况全覆盖 |

**设计理由**：AI 生成的代码往往只覆盖"快乐路径"。本阶段通过系统化的测试覆盖，确保产品在真实场景下的可靠性。

📄 **产出**：`docs/test-report.md`

---

#### 阶段七：部署上线

**目标**：确保代码与文档一致，规范化交付。

| 步骤 | 内容 |
|------|------|
| 📝 文档同步 | 将实际目录结构、部署方式、环境变量更新到架构文档 |
| ⚙️ CI/CD 配置 | 生成 GitHub Actions 等配置文件 |
| 📖 API 文档 | 生成 OpenAPI/Swagger 文档（如适用） |
| ✅ 部署验证 | 健康检查 + 冒烟测试 |
| 📄 生成 README | 编写最终项目 README.md |
| 🏷️ Git 标签 | 提交最终代码，打上版本标签（如 v1.0.0） |

📄 **产出**：最终 README.md + 版本标签 + CI/CD 配置

---

### 全局规则

| 规则 | 说明 |
|------|------|
| 🔄 **修改回溯** | 任何阶段可修改上一阶段内容，更新文档 → 重新确认 → 继续推进 |
| ⚖️ **需求冲突仲裁** | 发现新信息与已有文档冲突时，暂停操作，向开发者指出冲突 |
| 💾 **会话恢复** | 下次启动时，AI 自动读取 `docs/` 下的文档恢复进度 |
| 🔄 **终止与重置** | "重新开始" → 存档当前进度，退回 Phase 0 |
| 🎯 **单任务聚焦** | 始终保持"一次只做一件事"，禁止 AI 自由发挥超出规范范围 |

## ❓ 常见问题

### 需要会编程才能使用吗？

**不需要。** 你只需要描述你的想法，回答 Claude 提出的问题，确认每个阶段的产出物即可。代码由 Claude Code 生成。

### 支持哪些产品形态？

所有形态都支持：网站 / Web 应用、小程序、移动 App、桌面应用、浏览器插件、API 服务、命令行工具、Chrome 扩展等。

### 可以在已有项目中使用吗？

可以。使用全局 Skill 安装方式（方式二），在已有项目目录中启动 Claude Code 即可。

### 开发过程中可以添加新功能吗？

可以，但需要遵循回溯流程：更新 PRD → 重新确认 → 更新 TODO → 按小步迭代模式开发。

### 生成的代码质量如何？

经过以下质量保障：小步迭代模式（每次只改一个任务）、状态覆盖（加载/空数据/异常）、单元测试、全量代码审查、需求回溯（逐条对照 PRD）。

### 有英文版本吗？

有。请查看 [README.en.md](README.en.md)。
